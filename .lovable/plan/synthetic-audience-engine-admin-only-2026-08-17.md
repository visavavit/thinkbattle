# Synthetic Audience Engine (admin-only)

An admin tool that seeds a topic with believable synthetic activity: votes that trickle in over real time, likes/dislikes on real comments, and short AI-written takes posted in the correct side column. Public visitors see one combined number; admins see the real-vs-synthetic breakdown everywhere.

## What the admin controls

Per topic, a "campaign" with:
- Total fake votes (e.g. 500)
- Duration (e.g. over 6 hours) — the engine spreads them out
- Target split (e.g. 58 / 42) with a realism jitter slider
- How many synthetic comments (0-N) and how many reactions
- Persona tone: calm / casual / spicy (drives comment style)
- Start, pause, resume, stop, and "purge campaign" (removes every trace)

## What makes it look real (not a flat counter)

- **Traffic curve**: votes follow a decaying-interest curve plus a daily activity rhythm, so early hours are busiest and 3 a.m. is quiet. Never a constant rate.
- **Burstiness**: each tick draws a random count around the scheduled rate instead of an exact number, so counts are never suspiciously even.
- **Split drift**: the running split wanders around the admin's target with noise and slowly converges, instead of snapping to it.
- **Persona pool**: a reusable set of synthetic members with human-shaped usernames, varied join dates, and avatar initials. Each persona votes at most once per topic, and personas are reused across topics like real repeat visitors.
- **Comment realism**: short, lowercase-leaning, imperfect takes generated by the AI gateway from the topic title, the side, and the persona's tone; each comment lands at a random offset after that persona's vote (people argue after voting, not instantly). Duplicate/near-duplicate takes are rejected.
- **Reaction realism**: synthetic likes/dislikes are weighted toward real comments on the persona's own side, with a minority of cross-side dislikes — this is what naturally feeds the Wild Takes controversy metric.

## Admin visibility

A new "Audience" tab in the admin dashboard:
- Campaign list with progress bars (delivered / total, remaining time, current split)
- Per-topic breakdown: real votes vs synthetic votes, real comments vs synthetic
- Synthetic comments are badged in the moderation panel
- One-click purge per campaign

## Technical section

Database (migration):
- `bot_personas` — synthetic member pool. Each persona also gets a `profiles` row (profiles has no FK to auth.users, so this works) plus `is_synthetic` flag on profiles for admin-side filtering.
- `bot_campaigns` — topic_id, totals, target split, jitter, duration, status (draft/running/paused/done), delivered counters, curve seed, tone, created_by.
- `bot_actions` — planned schedule rows (persona_id, kind vote/comment/reaction, run_at, status). Planning up front makes delivery idempotent: a tick only claims due rows and marks them done, so re-runs never double-post.
- `is_synthetic` marker columns on `votes` and `comments` for admin breakdowns and clean purge.
- Admin-only RLS on all new tables via `has_role`; the delivery job writes through `service_role`.

Delivery:
- `src/routes/api/public/bots/tick.ts` — bounded worker called by pg_cron every minute, guarded by a shared-secret header. Per run: single-flight lease row, claim at most N due actions, execute, mark done, exit. Paused/stopped campaigns are skipped at the entry point.
- Existing spam guards already no-op when `auth.uid()` is null, so service-role writes pass; existing `sync_topic_votes` / `sync_comment_reactions` triggers keep all counters correct automatically.
- AI comments via the Lovable AI gateway, generated in small batches ahead of posting time and stored on the action row; circuit breaker halts the campaign on 402/403 and surfaces it in the admin UI.

Frontend:
- `src/components/admin/AudiencePanel.tsx` (campaign create/monitor), wired as a new tab in `src/routes/_authenticated/admin.tsx`.
- Campaign create/control through `createServerFn` with `requireSupabaseAuth` plus an in-handler admin role check.

Nothing on the public pages changes.
